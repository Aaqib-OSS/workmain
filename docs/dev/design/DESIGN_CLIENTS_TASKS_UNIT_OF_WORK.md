# clients_service and tasks_service on the unit of work — Design Study

**Status:** Active
**Kind:** Design study
**Author:** Spanner (Role 1)
**Date:** 20261116
**Originating item:** Issue #279

## 1. Purpose

Issue #279 moves `workmain/services/clients_service.py` and `workmain/services/tasks_service.py` from the session-taking form to the unit-of-work form (`docs/standards/4-database.md` §4.1). It fakes every repository method they call, gives the `clients` and `tasks` commands end-to-end tests with a recording renderer, and states the unit-of-work form in `docs/standards/5-cli.md` §5.6. They are the first services converted, so no converted service exists to copy. This study measures what the conversion touches, checks the issue's census against source, and sets out the choices whose answers change the spec.

### Settled by rule, recorded here so the spec can cite it

- **Fake storage and return values (F5, F6).** Each fake stores rows as dicts under `store['<table>']`, keyed by id, and assigns the id itself (#258 study F13). On each read it returns a new sessionless model instance built from the row. For a `TaskStatus`, that instance's `note` carries `created_date`, derived from `created_at` as the database derives it, and `meeting`. This is the only storage that `FakeUnitOfWork`'s deep-copy rollback accepts. Only the return type keeps the parity test's "answers as the real one does".
- **Seeding the rows the faked methods never write (F8).** `tests/mocks/fake_unit_of_work.py` gains one public seeding function that writes a row into a store in the fake's row form. Service tests seed through it. A contract class seeds its real side through the real repositories on `db_session`, and its fake side through this function. The issue's rule that only called methods are faked rules out faking `NotesRepository.create` and the other creating methods. `ClientRepository.create` is called, so it is faked and seeds clients on both sides, as the issue says.
- **Wildcards (F10).** The fakes match `%` and `_` literally, and no contract test puts either character in search text. `docs/standards/6-testing.md` §6.2 rule 8 says a test pins behaviour meant to stay and never exercises a path an open issue is about to remove. Until #219 lands, the fake and the real repository differ only on text that contains them.
- **§5.6 text (F17).** The converted-command bullet and the preview sub-bullet each state the unit-of-work form beside the session form: one `UnitOfWork` per use-case call, and the preview's unit of work exits before the question. The outside-action sub-bullet stays as it is and applies to the session form only, because no unit-of-work form for an outside call exists yet. `docs/standards/1-workflow.md` §1.5 requires every statement of the rule to change, which is why the preview sub-bullet is included.
- **Tests (F14–F16).** The `clients` and `tasks` command tests are replaced with end-to-end tests. `db_session` service tests become fake-unit-of-work tests. Behaviour that only the database shows (unlinking on delete, the `is_active` fallback) moves into contract tests run against both the real repository and the fake. The loading test moves to `tests/test_task_lifecycle.py`.

## 4. Options

### Q1 — The recording renderer's form

The question is real. §6.2's end-to-end command test needs a renderer that records what it is handed and never prints. The issue specifies a hand-written `Renderer` subclass in `tests/mocks/`, plus a test that each public method is in the subclass's own `__dict__`. That test exists because a subclass inherits every method it forgets to override, and the inherited method prints.

#### Option A — `create_autospec(Renderer, instance=True)`

- **Approach:** a `tests/conftest.py` fixture, `recording_renderer`, returns `create_autospec(Renderer, instance=True)`. A test reads the recorded calls with the standard `Mock` assertions. A test that reaches the picker sets `recording_renderer.pick.side_effect` to choose a candidate. The issue's sixth criterion is restated in the spec as: every public method of `Renderer`, current or added later, records rather than prints, checked by a test asserting none of them reaches a console.
- **Pros:** `docs/standards/3-code.md` §3.8 says to use the standard library's mechanism before writing your own. Autospec records every call and checks it against the real signature (F13). A method added to `Renderer` later is covered with no change, so the fall-through to printing that the issue guards against cannot happen. It is the form these tests already use (`Mock(spec=Renderer)`), with signature checking added.
- **Cons:** the issue's sixth criterion and its "subclasses `Renderer`" text are rewritten, and the issue body needs that edit at close-out (`docs/standards/1-workflow.md` §1.2). The recorded values are `call_args`, not named fields.

#### Option B — a hand-written subclass in `tests/mocks/`

- **Approach:** as the issue states. The subclass overrides each of the eight methods to append what it is handed to a list. `pick` returns a choice the test sets. A test asserts that each public method of `Renderer` is a key of the subclass's own `__dict__`.
- **Pros:** matches the issue text, and its criterion stands unchanged. A test reads named fields.
- **Cons:** it writes by hand what `unittest.mock` provides, and §3.8 requires the spec to record why. A method added to `Renderer` fails the `__dict__` test until someone writes its override, while autospec covers it with no change. It does not check call signatures.

**Recommendation:** Option A. It is the framework mechanism §3.8 prefers. It removes the defect that the issue's criterion only detects, and it continues the form these tests already use.

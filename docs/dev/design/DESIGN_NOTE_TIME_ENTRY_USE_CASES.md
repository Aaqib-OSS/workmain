## 1. Purpose

Issue #278 turns `notes_service.create_note`, `time_entry_service.create_paired_time_entry`, `time_entry_service.create_time_entry` and `time_entry_service.link_condensed_note` into operations on an entered unit of work (`docs/standards/4-database.md` §4.1). Each grouping of them becomes one use case, and every call site is moved so that no use case runs inside a `session_scope()` its caller holds open. The direction was settled in #258's study, Q6 (`docs/archive/design/DESIGN_UNIT_OF_WORK.md`). This study measures what the move touches on today's code and checks the issue's census against source. It also sets out the one choice whose answer changes the spec: where the condensed summary is written.

### Settled by rule, recorded here so the spec can cite it

- **Where the use cases live.** A use case that writes a note and nothing else goes in `workmain/services/notes_service.py`, which owns every note write. A use case that writes a time entry, alone or paired, goes in `workmain/services/time_entry_service.py`, which owns every time-entry write "including the time-entry half of every paired write" (`docs/ARCHITECTURE.md` §2). The pull stays in `clockify_service.apply_pull`, which is already its use case (F15). That module owns "push and pull".
- **One use case per grouping, and no use case calls another.** The groupings are: a note alone; a meeting note with its paired entry; a task-shaped entry with its note; and a condensed note with its linked entry. A use case cannot call another use case: a second entry raises, and so does the open-scope check. So the pull composes the operations `create_note` and `create_paired_time_entry` on the unit of work its caller passes in, as the issue directs (§4.1).
- **Use cases take ids and return plain values (F10, F11).** `link_condensed_note` takes a meeting id and a note id. Each use case returns a result type in its own module, named for its domain (`docs/ARCHITECTURE.md` §1 Result types), carrying the values its callers print.
- **`notes log` keeps per-line failure (F12).** Each line is one call of the note use case on a unit of work of its own, so a failed line rolls back alone, as its savepoint does today. Changing that to all-or-nothing is scope the issue did not ask for.
- **The call sites (F5, F16).** Each command reads what it needs inside its scope, as ids and plain values, and closes the scope before the use case. It opens a new scope for anything it reads afterwards: `time add`'s `plan_entry_push`. The `notes add` and `time add` prompts that follow a write stay where they are, between two use cases rather than inside a scope.
- **`ActionExecutor` (F13, F14).** As the issue directs, `ActionExecutor` takes no session. Its two callers stop opening a scope around `execute`. It opens a `session_scope()` for each handler that still takes a session, and builds a `UnitOfWork` for each that calls a use case. `_execute_create_time_entry` parses the start time with `workmain/utils/time_parser.parse_time`, which `docs/ARCHITECTURE.md` §2 makes the owner of clock times, so it needs no repository for that.
- **The pull (F15).** `apply_pull` takes a `UnitOfWork(record=True)` that `_pull_entries` builds for each entry, and enters it for the import. The link path keeps `_record_clockify_link`, which `push` shares and which #281 does not convert.
- **Tests (F3, F17, F18).** Under `docs/standards/6-testing.md` §6.2, the `db_session` tests of the four functions and of `apply_pull`'s import are replaced by tests on `fake_uow`. Each newly faked method gets a contract class run against the fake and the real repository. A test that used the functions only to seed rows seeds through repositories on `db_session` instead. The issue's third criterion says "with nothing patched". In the spec this means nothing between the command and the use case is patched. A condense path reaches the provider through `offline_provider_env` (F18), and the spec restates the criterion in those words (`docs/standards/1-workflow.md` §1.2).
- **The issue's first criterion (F2).** The spec restates its check so that it can see every form of a call from outside `workmain/services/`, an aliased import included (`docs/standards/1-workflow.md` §1.2, "a search that cannot see every form of what it counts proves nothing"). The issue body's edit is made at close-out.

## 4. Options

### Q1 — Where the condensed summary is written

The question is real. Today the summary, the condensed note and the linked entry are written as one unit (F6). The use case cannot run inside the scope that holds the condenser's write (§4.1), so one of the two writes has to move. Calling the condenser from inside the use case is not an option: it would make this issue the first provider-calling conversion, which #258 left to #262, and the condenser needs a session that a unit of work does not expose (F9).

#### The only valid option — the use case writes the summary with the note and the entry

- **Approach:** `condense_meeting` stops writing. It returns the summary it computed, and the rest of its return value is unchanged. The command closes its scope, which by then has only read, and calls one use case with the meeting id, the summary and its tags. That use case writes `condensed_summary` and `condensed_at`, creates the condensed note and links the entry, in one unit of work. The write goes through `MeetingsRepository`, which owns the meetings table: either `update` gains the two fields or a new method writes them. The spec names which. Its fake gets a contract class.
- **Why it is the only one:**
  - **The grouping belongs to the use case.** Under #258's direction, a use case decides once, for every surface, which writes commit together (`docs/archive/design/DESIGN_UNIT_OF_WORK.md` § The transaction belongs to the use case). Committing the summary in the command first would put that decision back in the caller, which is what this conversion removes. It would also split a unit that holds today (F6), and the resulting failure is silent: EOD stops offering the meeting (F7).
  - **It matches the converted form.** A capability returns plain values, and the application layer writes them through the repository that owns the table (`docs/ARCHITECTURE.md` §1 Capabilities and Data). The condenser's write moves out of a capability, the direction the known deficiency assigned to #208 points (F8). Leaving the write in place would be code #208 then removes. #208's own work is not done here: the condenser still queries through the session it is handed.
  - **It can be tested in the standard form.** "The summary, note and entry commit together" becomes a property of one use case, tested at the service on `fake_uow`, with the repository method under a contract class (`docs/standards/6-testing.md` §6.2). With the write in the command, no test owns that property.
- **What it costs:** a change to `workmain/ai/note_condenser.py`. No test asserts that the condenser writes the summary. The one assertion on it, `tests/test_note_condenser.py:338`, checks that a refused condensation leaves it unwritten, which still holds. One repository change, and its fake method with contract tests. The command's scope holds no write across the provider call, as today.

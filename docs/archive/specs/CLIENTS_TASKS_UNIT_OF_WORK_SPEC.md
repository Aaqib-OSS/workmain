## 3. Design rules

### Services

- **DR1 — Every public function is a use case.** Its first parameter is `uow: UnitOfWork` (`workmain/services/unit_of_work.py`) in place of `session`. It enters the unit of work once with `with uow:`, and builds and returns its result inside the block (`docs/standards/4-database.md` §4.2). Every other parameter, return type, raised exception and message is unchanged. The functions:
  - `clients_service`: `list_clients(uow)`, `get_client(uow, identifier)`, `add_client(uow, name)`, `preview_delete(uow, identifier, force)`, `delete_client(uow, client_id)`, `get_status(uow)`, `set_active(uow, name)`.
  - `tasks_service`: `list_tasks(uow, status, search, created, limit)`, `list_today(uow, search, today)`, `find_tasks(uow, identifier)`, `get_task(uow, note_id)`, `complete_task(uow, note_id)`, `dismiss_task(uow, note_id)`.
- **DR2 — Operations.** `tasks_service._task_for_note(uow, note_id)` takes a unit of work already entered and never enters it. `set_active` returns the active-client status read inside its own `with uow:` block, through a private operation that `get_status` also uses. A use case never calls another use case, because the second `with uow:` would raise (design study F11). `_resolve` and `_not_found` keep taking a `ClientRepository`, now `uow.clients`.
- **DR3 — Repositories come from the unit of work.** The services use `uow.clients`, `uow.notes` and `uow.task_status`, and construct no repository. Neither module imports `sqlalchemy` or a repository class, except that `clients_service` may keep its import of `ClientRepository` for `RESERVED_NAME`. Each module docstring states the unit-of-work form in place of "Functions take a session".

### Commands

- **DR4 — A command builds a unit of work for each use-case call.** Each command in `clients.py` and `tasks.py` calls its service as `service.fn(UnitOfWork(), ...)` and renders the result. Neither module imports `get_db` or opens a `session_scope()`. `clients delete` calls `preview_delete` with one `UnitOfWork`, renders the preview, asks `click.confirm` unless `--force` is set, then calls `delete_client` with a new one. `tasks`' `_pick_task` calls `find_tasks` with its own. Views, options, arguments, docstrings and every renderer call are unchanged.

### Fakes (`tests/mocks/fake_unit_of_work.py`)

- **DR5 — Storage.** A fake repository is built on the fake unit of work's store, as `FakeSystemStateRepository` is. It keeps rows as dicts keyed by id, under `store['<table name>']`, a dict created on the first write. The table names are `clients`, `notes`, `meetings`, `task_status`, `projects`, `report_recipients`, `reports` and `time_entries`. A method that returns a model builds a new `Client`, `Note`, `Meeting` or `TaskStatus` from the row on every call, with no session, and never stores it. DR6 states each table's row shape.
- **DR6 — Row shapes.** `docs/standards/6-testing.md` §6.2 has a test seed into `fake_uow`'s store "in the row shape its fake repository's docstring describes", so every table a fake reads has its row shape stated in a fake repository's class docstring. Every row holds every key of its shape, and a test writes the whole shape.

  Each table has one shape, stated in one docstring. Another fake that reads the table cites that docstring.
  - `FakeNotesRepository` states `notes` (`id`, `content`, `tags`, `created_at`, `meeting_id`, `client_id`) and `meetings` (`id`, `title`, `client_id`).
  - `FakeClientRepository` states `clients` (`id`, `name`, `is_active`, `created_at`), and `projects`, `report_recipients`, `reports` and `time_entries` (`id`, `client_id`). It reads `notes` and `meetings` rows in `FakeNotesRepository`'s shapes, which hold `client_id`.
  - `FakeTaskStatusRepository` states `task_status` (`id`, `note_id`, `status`, `completed_at`, `forwarding_note_id`, `created_at`, `updated_at`). It reads `notes` and `meetings` in `FakeNotesRepository`'s shapes.

  A note row has no `created_date`. The fake derives it on each read as `created_at.date()`, the derivation the computed column makes, so a seeded row cannot disagree with it.

  A row the fakes write themselves gets an `id` one more than the table's highest, or 1. `FakeClientRepository.create` writes `created_at` as `datetime.now(timezone.utc)`, aware, as `Client`'s default does. `set_completed` and `set_dismissed` write naive `datetime.now()`, as the real methods do. A naive time in one row and an aware one in another would make DR9's sort raise `TypeError`. So `notes` and `task_status` times, seeded or written, are naive local time, as `Note`, `TaskStatus` and the real repository write them (`workmain/database/models.py:208`, `:344-345`; `task_status_repo.py:100`, `:120`).

  No helper writes rows for a test. The standard has the test write them.
- **DR7 — `FakeClientRepository(store)`**, with all 10 methods. Each takes the real method's arguments and gives the real method's answer, including its `ValueError` messages word for word:
  - `create` refuses the reserved name, then a case-insensitive duplicate, as the real method does, and writes `is_active False` and `created_at`.
  - `get_by_name` compares `name.strip().lower()` with the stored name lowered.
  - `find_by_name_fuzzy` returns the clients whose lowered name contains `name.strip().lower()`. `list_all` returns every client. Both order by name in Python's `sorted` order, which is the order of the databases' `C.UTF-8` collation. `%` and `_` match literally.
  - `delete` returns `False` for an unknown id. Otherwise it removes the row, sets `client_id` to `None` on every row of the six linked tables that held that id, as `ON DELETE SET NULL` does, and returns `True`.
  - `count_linked_records` counts rows by `client_id` in the six linked tables, with keys in the real method's order.
  - `set_active`, `clear_active` and `get_active` set `is_active` as the real ones do, and write, delete and read `active_client_id` through `FakeSystemStateRepository(store)`. When the key names no client, `get_active` falls back to the flagged client with the lowest id. SQL leaves that order unstated, so no test seeds two flagged clients.
- **DR8 — `FakeNotesRepository(store)`**, with `get_by_id`. It returns a `Note` built from the row, whose `meeting` is a `Meeting` (`id`, `title`) built from `store['meetings']` when `meeting_id` names a row there, and `None` otherwise.
- **DR9 — `FakeTaskStatusRepository(store)`**, with all 5 methods.
  - A returned `TaskStatus` carries the row's columns, and its `note` is built as DR8 builds one.
  - `get_filtered` and `count_filtered` take only task_status rows whose note row exists, as the real inner join does. They filter by `status` unless it is `None` or `'all'`. They filter by `search` as a case-insensitive substring of the note's content, with `%` and `_` literal. They filter by `date_filter` against the note's `created_date`.
  - `get_filtered` orders by the note's `created_at`, newest first, with a `None` first (PostgreSQL's `DESC` puts NULLs first). `limit` 0 means no limit. Among notes with the same `created_at`, SQL leaves the order unstated, and so which rows a `limit` keeps. The fake keeps Python's stable sort order, and no test asserts the order of tied rows or which of them a limit keeps (DR13).
  - `set_completed` and `set_dismissed` raise the real `ValueError` for a note with no row. Otherwise they set `status`, `completed_at` and `updated_at` as the real ones do, and return the task.
- **DR10 — Signatures.** Each fake method has the real method's parameter names, defaults and annotations, and a fake has no public method the real repository lacks. `TestFakeParity.test_fake_methods_exist_on_real_with_equal_signatures` compares `inspect.signature(..., eval_str=True)` on both sides, so an annotation written as a string in one module and as an object in the other compares by what it names (§2). `fake_unit_of_work.py` imports every name its annotations use.
- **DR11 — Registration.** `FakeUnitOfWork.REPOSITORIES` gains `'clients': FakeClientRepository`, `'notes': FakeNotesRepository` and `'task_status': FakeTaskStatusRepository`.

- **DR14 — Service tests.** `tests/test_clients_service.py` and `tests/test_tasks_service.py` test each public function of DR1 with the `fake_uow` fixture (`tests/conftest.py`), its store seeded in DR6's shapes, and no `db_session`. Each test asserts the result's fields or the exception raised. A test of a write also asserts the store and `committed`. That includes `test_s14_delete_unlinks_linked_rows` and `test_s21_falls_back_to_the_flagged_client`: the fake reproduces both (DR7), and DR13's contract tests of `delete` and `get_active` show it does so as the database does.
- **DR15 — Command tests.** `tests/test_clients_commands.py` is rewritten, and `tests/test_tasks_commands.py` is new. `docs/standards/6-testing.md` §6.2 gives a command "one end-to-end test per path through it: each outcome of a flag, a prompt's answer or a pick". A path is a route through the command's own code. An option the command passes to its service unchanged adds no path, and the test that sets it shows the value reaching the service. The tests:
  - `clients add`, `clients list`, `clients show`, `clients set active` and `clients status`: one each.
  - `clients delete`, four tests. Prompt answered `y`: the client is deleted. Prompt answered `n`: `renderer.cancelled` is called and the client remains.     - `--limit 2`, `--status completed`, `--search` and `--date`: three tasks match every filter. 2 rows come back, the page total is 3, and the page's filters hold each value.
    - `--all` with the same `--limit 2`, `--status`, `--search` and `--date`, over the same seed: all 3 matching tasks come back. This is the `--all` path, where the cap is removed whatever `--limit` says.
  - `tasks today`, one test, with `--search` set.
  - `tasks show`, `tasks complete` and `tasks dismiss`, two tests each: the pick answered with a candidate, and the pick cancelled, where `renderer.cancelled` is called and nothing is changed.

A cancelled pick sets `recording_renderer.pick.side_effect` to return `None`.

## 7. Risks and rollback

- **A fake that answers differently from the SQL in a case no contract test covers** lets a service test pass while production differs. The contract tests cover each behaviour DR7–DR9 names. The cases left uncovered on purpose are the four DR13 names.
- **A command test that seeds through `db_session` and runs a command whose unit of work opens its own session.** The issue's probe of 20261116 shows the unit of work sees the seeded rows, even rows only flushed, and finishes first, the last-in, first-out order `tests/conftest.py`'s `_isolated_database` docstring states.
- **Rollback:** each step is one commit and is reverted on its own. Steps 3 and 4 each revert a service, its commands and its tests together. Step 1's fakes are used only from step 3 on.
